# Contributor documentation

Treat the repository’s existing documentation and how contributors keep it current as part of the quality floor. Start at the existing contributor entry point. Record the architecture decisions that change how someone should implement the next feature. Keep the explanation beside existing architecture or development guidance. A small project can use a short section in its README. Create a separate document when people need to consult or maintain it independently.

For a representative change, point from the entry point to the owner and its supported extension path. Record the boundary that matters on that path and why it exists. Depending on the change, that means permitted dependencies, who may update state or release a resource, where errors become public, or which work stays off a hot path. Point to a real example that contributors can extend. Give the reason to use that path, including a shortcut that would split a responsibility or add work to a shared path. Record current design and any proposed migration separately.

Make the explanation usable by someone with only the checkout. They should find the editable policy, the commands for fast and full checks, how a rejected change can be repaired, and who owns any versioned public contract. Describe protections that follow from the code and how a contributor can confirm them. For tagged rules, name a registered compiler, static or behavior check only to the extent it enforces the rule. Use `[unchecked: reason]` for judgments that have no such check. If a tagged rule is enforced by code outside the gate, record that mechanism in the unchecked reason and point to its proof. Verify that each stated boundary matches the code, and exercise the path another contributor would follow. A link check proves that the destination exists.

Use one editable guidance source for each decision. Link human and agent entry points to it. Update the explanation with the contract it describes, and record separately owned exceptions or migration decisions with their reasons.

Keep the distinction the repository uses between design decisions, public reference, and evidence such as measurements, research or known limits. Use each as a source when selecting the floor. Update the owning document and related contract fixtures in the same change when a decision, interface or supported example moves.
