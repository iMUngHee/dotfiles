# Project bootstrap

Agents copy what the repository already contains, and a rule nothing enforces is a suggestion. Leave the repository so that its conventions fail in a gate, its existing debt can only shrink, and every correction made later turns into a check. A request to discuss or design produces a proposal; an explicit setup request includes applying and checking the result.

1. **Read the project.** Locate the repository or package, including an empty directory. Inspect its owning instructions, human docs, manifests, tool settings, source, tests, task runner, CI and release history. Follow generated headers to the editable source. In a mixed repository respect root policy and keep package work local.
2. **Infer the maintenance routine.** What someone changes, which behavior must survive, how it is checked and where the rules live. Use explicit current directions, existing practice, supplied preferences, then the stack's supported defaults ([defaults](references/defaults.md)). Distinguish a preference from a request to migrate, and say which choice you kept when local convention and supplied taste differ.
3. **Ask only what decides the outcome.** Proceed with reversible choices. Ask when guessing would decide correctness or start an expensive migration; give the recommended answer in plain words. A clear repository can need zero questions.
4. **Install the gate.** One `scripts/check.sh` with fast and full tiers and a pre-push hook, from the bundled assets and their contract ([gate](references/gate.md)). Extend an existing gate instead of adding a second; connect existing CI to the same script and create none.
5. **Make conventions fail.** Wire the stack's formatter, linter, suppression-with-reason, ban-with-message, type, boundary, test, dead-code and audit capabilities into the gate ([stacks](references/stacks.md)). Turn on what the code already satisfies; put what it breaks into `banned-patterns.tsv` with `mode=ratchet` and write the baseline. Add the repository checks its rules call for: work-artifact and workaround comments, surface inventories against their reference docs, layering, generated sources, changelog and version. Show each new check failing on a real or reproduced mistake before relying on it.
6. **Choose verification by risk** ([verification](references/verification.md)): property-based tests, fuzzing with its crash corpus replayed in fast, differential and mutation tests where they answer a real question. Report model-checking and proof candidates with the promise each protects; add them only on the maintainer's decision, with a pinned toolchain, a `formal.tsv` record the gate checks for drift, and the seeded `formal.md` rule. Where `statechart` is installed, name it to the maintainer for drawing a TLA+ model with the shortest path to each broken rule; it runs only when invoked explicitly.
7. **Write the guidance.** Keep one editable agent-guidance source and its loaders; for a new two-tool layout use the [agent file builder](assets/agents-build.mjs) as [defaults](references/defaults.md) describes. Rules are short and every rule item ends with `[check: …]` or `[unchecked: reason]`; their reasons go in a development guide for humans, together with the criteria for choosing test cases from [verification](references/verification.md). Seed the maintenance rule and the code-review, rule-docs-sync and garden skills, plus the conditional skills the repository gives a reason for ([skills](references/skills.md)). Treat existing README, code and configs as evidence and keep their bytes unless the setup needs a change; for a handwritten AGENTS.md keep every byte and append only what is missing. Keep the generated AGENTS.md within the 32 KiB Codex reads by default; the bundled builder fails beyond it, and an existing builder gets the same check. Keep personal addresses, home paths, machine details and global assistant rules out of the repository.
8. **Prove it.** Run `scripts/check.sh --fast` and `scripts/check.sh` in the repository. Plant one violation per repository check and confirm each fails with its hint, then remove them. Run the builder again or its `--check` for idempotence and inspect the working-tree diff, including untracked files. Report the editable sources, the gate entrypoints, what each tier runs, the ratchet baselines with their counts, the share of `unchecked` rules, formal-verification candidates, the version owner or deferral, any check you could not run, and every file the session could not write (such as a hook path a permission policy blocks) with the exact commands a person runs to finish it. Release publishing is a separate action.
