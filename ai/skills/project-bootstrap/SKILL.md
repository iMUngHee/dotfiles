# Project bootstrap

Start from the maintainer's request and the project they actually have. Use [the decision reference](references/defaults.md) to fill gaps. A request to discuss or design produces a proposal. An explicit setup request includes applying and checking the result.

1. Locate the requested repository or package, including an empty directory. Inspect its owning instructions, human docs, manifests, tool settings, source, tests, task runner, CI and local release history where available. Follow generated headers to the editable source. In a mixed repository respect root policy and keep package work local.
2. Infer a concrete maintenance routine: what someone changes, which behavior must survive, how to check it and where the rules live. Use explicit current directions, existing practices, supplied preferences and then the stack's supported defaults. Read personal references only when supplied. Distinguish a preference from a request to migrate. When local convention and supplied taste differ, tell the maintainer which choice you kept and what switching would change (for example, a repository-wide reformat).
3. Proceed with sensible reversible choices. Ask about broad intent only when it is missing and affects the outcome. Ask a targeted question when guessing would decide correctness or an expensive migration. Defer details that can wait. Give the recommended outcome in ordinary language; skip questions already answered by the repository. A clear repository can need zero questions.
4. Choose the editable agent guidance and its loader paths as the default write scope. For a maintenance setup with working tools, write inferred conventions, verification and version decisions there once. Treat the existing README, code, configs and checks as evidence; keep their bytes intact unless the request specifically calls for changing them or a concrete missing capability requires it. A second explanation in a README is not a missing capability. Preserve an existing check or generator and use its normal entrypoint. For a handwritten AGENTS.md retain every existing byte, append only genuinely missing project-specific guidance, and show the diff. Add a missing CLAUDE.md import when appropriate. Preserve independent tool instructions; show conflicts before converting ownership. Put recurring project work into a skill when there is a concrete workflow. Keep speculative skills, empty registries, sample policies and unused workflows out of the tree.
5. For a new shared-source layout follow the reference. Use the optional [agent file builder](assets/agents-build.mjs) only where it fits the project's runtime and loader capabilities. Verify the actual loader paths of each concrete skill. Keep personal addresses, home paths, machine details and global assistant rules out of shared project artifacts.
6. Run the existing safe verification command in its owning directory. Check its observable result and the working-tree diff, including untracked outputs. Exercise the generated layout again for idempotence or use its read-only check. Inspect changed paths against the chosen scope. Report the editable source, exact verification entrypoint, version owner or deferral, and any manual, costly or unavailable proof. Release publishing is a separate action.
