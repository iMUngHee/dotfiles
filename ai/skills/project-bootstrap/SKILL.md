# Project bootstrap

Finish when a contributor with only the repository can change code, run its gate, and maintain its rules. A design request ends with a proposal. A setup request includes installing and proving the selected controls.

1. **Read a change path.** From the owning package trace a typical edit through its public contract, state or resource owner, dependencies, and existing checks. Inspect human and agent instructions, generated headers, manifests, CI and release history. Respect root policy and package scope. For an empty project ask its purpose only if unknown; defer language-specific controls until the stack is known.
2. **Choose the target.** Use reasoned project decisions, maintainer preferences, published guides actually read, then supported stack defaults ([conventions](references/conventions.md)). Existing practice is evidence. For each new constraint identify a credible failure and a nearby valid choice that must remain possible. Check responsibility, dependency direction, types, errors and implementation costs before style. Infer reversible defaults; ask only if the answer changes correctness, compatibility or a costly migration ([defaults](references/defaults.md)).
3. **Choose where to prevent each failure.** Prefer a small ownership, visibility, API or type decision when it makes the mistake hard to express. Enforce the policy at the boundary that owns it. Limit claims about a passing check to the paths and environment it exercised. Keep disruptive product redesign as a follow-up. Where the mistake remains possible, use an existing compiler, lint or boundary check that can distinguish the two cases ([stacks](references/stacks.md)). Use a behavior check or measurement for a contract observable only at runtime ([verification](references/verification.md)). Leave decisions that require context to review. Preserve existing effective checks.
4. **Install and prove the gate.** Extend one repository gate with fast and full entrypoints, route existing CI and the clone-local pre-push hook to that gate. If the Git repository lacks the hook, install a small hook that invokes its fast entrypoint and enable it for this clone, preserving any existing hook chain. Keep a working gate in place; add only the selected checks it lacks. Copy the bundled driver only when creating a gate and its registration model has a concrete consumer ([gate contract](references/gate.md)). A small script can serve both tiers when their checks coincide. Scope each new check to the owner; demonstrate the failure with its repair hint and the closest legitimate look-alike passing. If a cheap approximation blocks a valid change, narrow it or leave the decision to review. Baseline existing machine-detectable violations when introducing a ratchet. Run fast and full, recording any unavailable proof.
5. **Hand maintenance to the repository.** Keep one editable guidance source, preserve handwritten instructions and extend them only as needed. Use the [loader defaults](references/defaults.md#shared-source-and-discovery) for generated surfaces and verify discovery, idempotence and the 32 KiB generated AGENTS.md limit. Tag rule items with their actual check or an unchecked reason. Show contributors where to change a policy, how to sync it and how to verify a changed exception. Identify the owner of each versioned contract or explain why versioning is deferred ([documentation](references/documentation.md), [skills](references/skills.md)). Keep private paths and global configuration out. Inspect tracked and untracked changes. Report what now blocks a violation, what reviewers still decide, important exceptions or debt, and exact steps for anything the environment prevented. Publishing is separate.
