# Project bootstrap

Leave code that gives the next contributor a sound way to extend it. The repository should retain its architecture, implementation standards and public contracts as people and agents change it. A proposal describes the selected interventions and their proof. An installation makes them work from the checkout and hands their upkeep to the repository.

1. **Find what the project must keep.** Read the purpose, design and research records, contributor conventions and public surfaces. Check the owners of persisted state, dependency boundaries, costly execution paths and existing protections wherever they matter. Trace a representative change through the actual code, then follow another path when a consequential promise falls outside that trace. For an empty project use the first intended change and protect what is already known.
2. **Set a project standard before choosing a tool.** Use reasoned project decisions, maintainer preferences, applicable published guidance you have read, then supported stack defaults. Existing code is evidence. For each consequential decision, identify a technically working change that would make the code worse and a legitimate alternative to preserve. Include the failure's effect on later changes or on an actual workload. See [conventions](references/conventions.md).
3. **Make the good path easy to follow.** Trace the intended extension through its owner, API and types. Keep a sound implementation as the example. Where a credible shortcut remains, use a small compatible change that gives responsibility to its owner or makes the invalid path harder to express. Check delegation, duplication and resource cost at their actual callers. Record a costly migration with the existing boundary and its reason. See [structure](references/structure.md).
4. **Protect what remains and prove the difference.** Exercise the intended extension or nearest relevant call and a realistic violation. Show how the code or compiler rejects the violation when it can. Use precise static checks for remaining repeatable violations, use behavior tests or measurements for contracts that require running the code, and name judgments reviewers still own. For a replacement, prove the old protection's effective scope before retiring it. Reuse the working gate and its entry point. Run the applicable tiers, connect existing CI and enable or extend the clone-local pre-push hook. See [gate](references/gate.md), [stacks](references/stacks.md) and [verification](references/verification.md).
5. **Hand it over once.** Leave a working code example, its important decisions and scope, the existing documentation and commands that keep the decision current, and how to maintain the enforcement or update an exception. From the checkout, verify that a contributor can find and follow the intended extension path. State what the structure prevents, what runs in a check, and what remains for judgment. Record current debt, deferred migrations and any evidence you could not obtain. See [documentation](references/documentation.md), [loader defaults](references/defaults.md#shared-source-and-discovery) and [maintenance](references/skills.md).
