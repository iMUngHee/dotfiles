# Project bootstrap

Make the repository carry its quality floor. A contributor with only the checkout should be able to find where a change belongs, preserve the project's contracts, run its checks and evolve its rules. A design request calls for a proposal. A setup request includes making and proving the selected changes.

1. **Trace a representative change.** Start with the project's purpose and what would make a technically working change costly to keep. Follow a real entry point through the public contract, responsibilities, dependencies, and the owner of any state or resource. Inspect the existing tests, instruction sources, manifests, gate, CI and release history that bear on that path. On an empty checkout, use the first intended use case and defer decisions that need a known stack.
2. **Set the engineering standards.** Start with reasoned project decisions, then maintainer preferences, applicable published guidance you have read, and supported stack defaults. Use existing code as evidence and identify patterns contributors should copy or avoid. Consider architecture, semantics and implementation cost before idiom and style. For a consequential standard, identify the failure it avoids, what a valid choice looks like and why it fits this project. See [conventions](references/conventions.md).
3. **Make the structure carry the decision.** Put responsibility and state with their owner. Use the smallest compatible change to dependency direction, visibility, API or types that makes a credible mistake hard to express. Prefer an existing sound path contributors can extend. Weigh migration cost, compatibility and risk. Record larger redesigns as follow-up decisions with the present boundary clear.
4. **Protect and prove the remaining contracts.** Use the compiler, existing lint or a precise boundary check for decidable violations. Use existing behavior checks or representative measurements for important runtime gaps. Document judgments reviewers must make. Prove the adopted boundary with a realistic disallowed change and a nearby legitimate one. For a new check, confirm the diagnostic explains the repair. Scope rules to their owners and ratchet existing violations when appropriate. Preserve effective existing checks. Reuse one repository gate and its entry point. Run fast and full tiers, connect existing CI and enable or extend the clone-local pre-push hook. See [gate](references/gate.md), [stacks](references/stacks.md) and [verification](references/verification.md).
5. **Leave decisions where contributors need them.** From the existing contributor entry point, show the representative change path, its owner, the meaningful boundary or contract and its rationale. Distinguish current behavior from a planned change. Point to a sound example, the policy's editable source and the mechanism or review that protects it. Give contributors standard commands and a way to update the decision, its enforcement and generated guidance together. Verify the handoff from the checkout, including any [loader work](references/defaults.md#shared-source-and-discovery). Report what is protected, what remains for review, relevant debt and any unavailable proof. See [documentation](references/documentation.md) and [maintenance](references/skills.md).
